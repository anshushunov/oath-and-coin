# ADR-003 — Counter-based RNG без хранимого состояния

> Дата: 2026-08-13
>
> Статус: accepted (решение владельца по Gate 0, 2026-08-13)

## Контекст

`TDD` §7.1 требует, чтобы одинаковые `ruleset_version + content_version + seed` давали одинаковый результат, а §7.2 — независимые потоки случайности. `System.Random` этого не даёт: платформа не гарантирует одинаковую последовательность между версиями .NET, поэтому replay перестанет сходиться при обновлении SDK — без единого изменения в правилах и без внятной диагностики.

Спека Gate 0 предлагала PCG32 или xoshiro256\*\* и оставляла выбор открытым до этой записи. Реализация спайка уточнила требование: генератор должен быть не просто хорошим, а **вызываемым из чистой функции перехода состояния**.

## Решение

- **Случайность — чистая функция:** `DeterministicRng.Draw(campaignSeed, stream, ordinal)`. Ни объекта генератора, ни поля, ни счётчика внутри типа.
- **Алгоритм:** две композиции финализатора SplitMix64. Поток подмешивается в первый проход и даёт ключ потока; порядковый номер — во второй и даёт саму выборку. Значение зафиксировано строкой версии `splitmix64-composed/1`.
- **Потоки** — перечисление `RngStream` по `TDD` §7.2: генерация мира, тик мира, генерация контрактов, решения героев, события экспедиции, бой, косметика представления.
- **Порядковый номер живёт в состоянии,** а не в генераторе: `GameState.Metadata.NextDecisionOrdinal`. Движок остаётся без полей.
- **Отклонённая выборка учитывается:** `DrawInt32` возвращает `Int32Draw` с числом сожжённых ординалов, а `GameState.WithEvent` требует передать это число третьим параметром. Диапазон выбирается rejection sampling, чтобы каждое значение было равновероятным.

## Альтернативы

- **`System.Random`** — отклонено: последовательность не стабильна между версиями .NET; дополнительно `new Random()` в core не компилируется, потому что пространство имён `OathAndCoin.Simulation.Random` затеняет тип.
- **PCG32 или xoshiro256\*\*** (предложение спеки) — отклонено не по качеству потока, а по форме: это последовательные генераторы с состоянием. Их пришлось бы либо хранить в `GameState` как изменяемый объект, либо прокручивать от начала кампании при каждой загрузке. Counter-based-схема даёт replay и save/continue без того и другого; SplitMix64 — тот самый примитив, которым эти генераторы засеиваются, и для целочисленных решений его достаточно.
- **Один общий поток на всю симуляцию** — отклонено: изменение числа выборок в одной подсистеме сдвинуло бы последовательность во всех остальных.

## Последствия

- Воспроизводимость следует из чистоты функции, а не из аккуратности вызывающего: одно и то же состояние с одной и той же командой даёт один и тот же результат всегда.
- `AlgorithmVersion` версионируется: смена алгоритма или порядка подмешивания — ломающее изменение replay всех сохранённых кампаний, требующее новой записи.
- Плата за честность: число сожжённых ординалов передаётся вручную. Компилятор заставляет передать число, но не правильное число — это контракт, а не механизм, и он назван в комментарии к `WithEvent`.
- Замороженный golden vector делает алгоритм частью контракта: молча «улучшить» перемешивание нельзя.

## Проверка

Реализация: `simulation/OathAndCoin.Simulation/Random/DeterministicRng.cs`, `RngStream.cs`, `Int32Draw.cs`.

Тесты, которые сломаются при отмене решения: `tests/OathAndCoin.Simulation.Tests/DeterministicRngTests.cs` — `Draw_IsPureFunctionOfItsArguments`, `Draw_MatchesCommittedGoldenVector` (падает при любой смене алгоритма), `Draw_DiffersAcrossStreams`, `Draw_DiffersAcrossOrdinals`, `DrawInt32_ReportsEveryOrdinalARejectionBurned`. Сквозная проверка — `tests/OathAndCoin.Content.Tests/ReplayDeterminismTests.cs` и стадия determinism replay в CI.

Пересмотр — если профиль покажет стоимость двух перемешиваний на выборку значимой в batch-прогонах баланса, или если понадобится распределение, для которого целочисленной выборки недостаточно.
