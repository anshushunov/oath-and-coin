# Oath & Coin — план разработки MVP

> Версия: 0.1
>
> Статус: proposed
>
> Связанный документ: [`../design/GDD.md`](../design/GDD.md)

## 1. Цель плана

Этот документ превращает продуктовый замысел GDD в последовательность проверяемых этапов. Он не выбирает технологический стек и не заменяет system specs.

Главный принцип производства:

> Сначала доказать, что автономные герои дают игроку интересные, предсказуемые и пересказываемые последствия. Только потом наращивать мир и контент.

## 2. Что здесь называется MVP

Чтобы разные агенты не использовали слово `MVP` для разных результатов, вводятся пять уровней:

| Уровень | Назначение | Доступность |
|---|---|---|
| Proof of Fun | Проверить одну рискованную механику | Внутренний |
| First Playable | Замкнуть минимальный игровой цикл | Внутренний |
| Vertical Slice | Показать целевое качество одного фрагмента | Закрытые тесты |
| External MVP | Проверить продукт на внешних игроках | Ограниченная публикация |
| Content Complete | Наполнить объём первой версии | До релиза/EA |

Раздел 18 текущего GDD описывает в основном **External MVP**, а прототипы A–C — более ранние доказательные этапы.

## 3. Северная звезда и kill criteria

### 3.1. North-star outcome

После короткой серии контрактов игрок может объяснить:

- почему он выбрал конкретных героев;
- почему герои согласились или отказались;
- почему они повели себя определённым образом;
- как прошлое изменило следующий выбор;
- какую историю создали последствия.

### 3.2. Kill/pivot criteria

Концепция требует пересмотра, если после двух качественно разных прототипов:

- автономия по-прежнему воспринимается преимущественно как случайность;
- объяснения AI понятны, но не влияют на последующие решения игрока;
- оптимальная стратегия сводится к выбору максимальных характеристик;
- игрок постоянно хочет прямого управления, даже имея достаточные инструменты подготовки;
- прошлые события не меняют эмоциональную или стратегическую ценность героев.

Такой результат не означает закрытие проекта автоматически. Он требует отдельного решения: менять модель автономии, степень контроля или основную фантазию.

## 4. Gate 0 — production contract

Gate 0 намеренно минимален: он принимает только решения, без которых нельзя написать первую строчку production-кода. Остальные решения принимаются внутри майлстоунов, когда становятся блокирующими фактически, а не по списку. Урок Dungeon Fortress: фронт-лоуд церемонии до кода убивает темп, не снижая риск.

### 4.1. Блокирующие решения Gate 0

Четыре блока:

1. **Стек и прототипная платформа** (`ADR-001`); критерий №1 — скорость агентной итерации: headless-тесты, CLI, отсутствие немержимых артефактов. До M4 действует desktop-предположение; выбор первой целевой платформы и input остаётся за M4.
2. **Граница simulation core и контракт events/causal trace** (`ADR-002`, `ADR-007`).
3. **Deterministic RNG** (`ADR-003`).
4. **Формат контента и схема стабильных ID** (`ADR-004`, `ADR-005`).

Реестр всех технических ADR и сроки их принятия — TDD §21.

### 4.2. Решения, перенесённые в майлстоуны

| ID | Решение | Принимается не позже |
|---|---|---|
| G0-D1 | Граница контроля | направление зафиксировано в [DEC-005](../decisions/DEC-005-retreat-signal.md) (proposed, принятие после M2); остаток — M1/M2 |
| G0-D2, G0-D3 | Пространство и время боя | принято: [DEC-011](../decisions/DEC-011-combat-space-and-time.md) — поле 3×3, отряд 4–6, дискретные такты и перестановка; геометрия — за `Combat System Spec` |
| G0-D4 | Окончание First Playable | старт Milestone 3 |
| G0-D5 | Сохранения, повтор боя, permadeath | Milestone 3 |
| G0-D6 | Тон мира | Milestone 3 (прототипы используют placeholder-тон) |
| G0-T2 | Первая платформа и управление | Milestone 4 (до этого — desktop-предположение) |
| G0-T5 (часть) | Версионирование сохранений | Milestone 3 (`ADR-006`) |
| G0-T6 | Тестовый runner | вытекает из ADR-001, фиксируется в spike без отдельного ADR |

### 4.3. Результат Gate 0

- принятые `ADR` четырёх блоков (§4.1);
- **контрактный пакет в коде**: скелет `GameState`, конверт события, схема ID, интерфейс `DecisionResult` (TDD §8) и базовые фикстуры — компилируемые типы, а не проза;
- simulation spike из TDD §23, подтверждающий воспроизводимость seed одной headless-командой;
- CI: форматирование, тесты, проверка данных, replay-тест детерминизма.

Gate 0 завершён после ручного подтверждения владельцем продукта. Шаблоны спек и задач создаются по мере первой необходимости, а не как условие гейта.

## 5. Milestone 1 — Hero Decision Lab

### 5.1. Вопрос

Может ли игрок воспринимать отказ и автономный выбор героя как следствие характера, а не как помеху или случайность?

### 5.2. Scope

- шесть заранее подготовленных героев;
- компактная модель из 6–8 черт/ценностей;
- доверие к гильдии и простое отношение между героями;
- один шаблон контракта с несколькими параметрами риска и награды;
- выбор отряда из четырёх героев;
- согласие, отказ и минимальный срез переговоров ([DEC-008](../decisions/DEC-008-negotiation-first-differentiation.md)): одно денежное условие, одно ценностное ограничение, одно обещание, одно нарушение и одно последствие для героя/свидетеля;
- машинный causal trace и короткое объяснение игроку;
- 20–30 фиксированных сценариев;
- простой текстовый или функциональный UI.

### 5.3. Вне scope

- бой;
- карта мира;
- предметы и способности;
- визуальная база гильдии;
- процедурная генерация контента;
- сложная экономика;
- долгосрочная кампания.

### 5.4. Ключевые решения до реализации

- utility model или rule/priority model;
- форма публичного объяснения без показа внутренней математики;
- предел влияния награды на ценности и страх;
- механизм конфликта нескольких мотивов;
- правила стабильности поведения между похожими ситуациями.

### 5.5. Exit criteria

- не менее 70% тестеров правильно предсказывают выбор минимум четырёх из шести знакомых героев;
- не менее 70% могут назвать две главные причины решения после просмотра объяснения;
- изменение одного понятного условия предсказуемо меняет решение в контрольных сценариях;
- нарушенное обещание создаёт последствие, которое тестеры пересказывают без подсказки;
- каждый результат воспроизводится по seed;
- ни один герой не описывается тестером только через класс или силу;
- нет одной величины награды, которая подавляет все остальные мотивы без специальной черты.

### 5.6. Deliverables

- `Hero Decision System Spec`, включая модель переговоров, обещаний и их нарушения;
- schema героя, отношений и предложения контракта;
- decision simulator;
- trace viewer/log;
- automated scenario suite;
- отчёт playtest и решение о переходе к Milestone 2.

### 5.7. Незакрытый остаток на 2026-08-22

Ядро решения героя реализовано (`m1-decision/1`), **срез переговоров из [`DEC-008`](../decisions/DEC-008-negotiation-first-differentiation.md) §1 — нет**, playtest не проводился. До закрытия этого остатка расширять пространство переговоров нельзя: DEC-008 §1 разрешает расширение только после подтверждения гипотезы в M1.

Две гипотезы §5.5 проверяются раздельно, и первая не требует нового кода ([`DIRECTION_2026-08`](../research/DIRECTION_2026-08.md) §2.1, §7):

- **H-A1, механическая читаемость** — игрок предсказывает ответы, называет причины и указывает условие, которое перевернёт ответ. Обязателен контроль переносом на **новый** контракт с теми же метками, иначе измеряется заучивание конкретных контрактов.
- **H-A2, восприятие личности** — измеряется **отдельно и после паузы**: различить двух героев с похожими ответами, описать каждого своими словами, назвать ожидаемое противоречие, объяснить кадровое предпочтение. Из H-A1 не следует: можно безошибочно предсказывать «Мира отвергает обман» и воспринимать Миру как строку таблицы. Пересказ текста трассы доказательством не считается. Сюда же относится критерий §5.5 «ни один герой не описывается только через класс или силу» — ему нужен проверяемый порог, а не оценка на глаз.
- **H-B, петля** — требует среза DEC-008 и минимального двухшагового протокола: выбор пакета и обещания → явное последствие → **второй сопоставимый выбор игрока**. Засчитывается, только если игрок изменил второй выбор **и** может назвать связь с последствием. Изменение ответа пострадавшего и свидетеля — это переход состояния симуляции, а не петля игрока, и в доказательство H-B не входит.

Ценностное ограничение в срезе — **выбираемая метка контракта** (`method:deception` против `method:open`), а не новая сущность: `inclination` и `principle` уже дают каждому герою персональную оценку метки, и трасса уже умеет её объяснять.

Срез специфицирован 2026-08-22: [`NEGOTIATION_SPEC`](../technical/NEGOTIATION_SPEC.md), продуктовое решение — [`DEC-012`](../decisions/DEC-012-negotiation-offer-protocol.md). Он требует снятия байтового паритета с корпусом миграции ([`ADR-013`](../decisions/ADR-013-retiring-corpus-parity.md)): корпус пиннит контент, форму состояния и версию правил одновременно, а срез меняет все три.

## 6. Milestone 2 — Combat Lab

### 6.1. Вопрос

Может ли подготовка к короткому автобою быть интересной, а исход — достаточно читаемым для обучения?

### 6.2. Scope

- отряд 4–6 героев против 2–6 противников;
- **поле 3×3** ([`DEC-011`](../decisions/DEC-011-combat-space-and-time.md)): поле намеренно больше отряда, пустая клетка — уязвимость, открытая колонка в первом ряду открывает тыл. **`DEC-011` принимает размер поля, но не геометрию:** правила доступа к целям, прикрытие колонкой, разрешение сдвига, цена перестановки, **выгода** пустой клетки и численная асимметрия закрываются `Combat System Spec` до контента. Без выгоды у пустой клетки рациональной базой становится «заполнить передний ряд», и решение о дырах исчезает;
- геометрия и идентичность рядов валидируются **при равной численности**; бои 4 против 6 — отдельные сценарии с заранее названной ожидаемой степенью преимущества, потому что при одном действии на героя численность сама по себе даёт полуторную экономику действий;
- каждый ряд несёт механическую идентичность (столкновение / опора / тыл), способности привязаны к рядам; ряд без собственной идентичности — декорация;
- перестановка внутри боя — дискретная, отдельным действием, а не свободное перемещение: это удерживает трассу однострочной («отступил в тыл, потому что ранен») и не заводит поиск пути;
- сбить героя с его ряда — способ отключить половину его набора действий, а не отнять здоровье;
- четыре боевые роли;
- 1–2 способности на героя, перк со специализацией, снаряжение как модификатор роли — основная глубина живёт здесь, а не в геометрии;
- стартовое размещение;
- одна групповая доктрина и условия отступления;
- одна личностная реакция, способная изменить действие;
- намерения, пауза, скорость и battle log;
- causal trace каждого значимого выбора;
- headless batch simulation.

### 6.3. Вне scope

- мировой маршрут;
- фракции;
- полноценный loot/crafting;
- многоэтапные боссы;
- большой roster;
- окончательный арт и анимации.

### 6.4. Exit criteria

Каждый критерий называет выборку, базу сравнения и порог. Формулировки вида «заметно влияет» и «хочется разобрать» без протокола непроверяемы и в этот список не входят.

**Главный критерий, и он не про бой** — без него лаборатория может пройти всё остальное как обычный позиционный автобаттлер, не проверив дифференциатор ([`DIRECTION_2026-08`](../research/DIRECTION_2026-08.md) §4.8):

- два **механически сопоставимых** героя (или состава равной силы) ведут себя в бою по-разному из-за уже существующего мотива или отношения, а не из-за характеристик, — и тестер **использует это знание при следующей подготовке**: в выборе состава, капитана или доктрины. Если знание человека не меняет подготовку, бой не выполняет роль шва между слоями, каким бы интересным он ни был.

Остальные:

- после поражения не менее 70% тестеров называют хотя бы одну изменяемую причину;
- минимум два разных состава/плана контрят разные типы угроз;
- перестановка или доктрина меняет исход: на **замороженном до балансировки** наборе seed'ов распределение побед при смене расстановки отличается от базового сверх заранее заявленного порога;
- личностное нарушение доктрины телеграфируется и объясняется, а его доля попадает в заранее объявленный коридор — «редко» без числа не измеряется;
- нет доминирующего состава на **held-out наборе угроз**, отобранном до балансировки. Контрольный набор, собранный после неё, доказывает только то, как его собирали, а два авторских контра удовлетворяют критерий без интересной подготовки;
- массовый прогон обнаруживает инвариантные ошибки и сохраняет проблемный seed;
- каждый из трёх рядов различается в решениях игрока: контрольный набор боёв показывает, что перенос героя между рядами меняет исход, а не только текст;
- длина боя измерена batch-прогоном до появления арта **числом раундов**, а не ощущением; желание разобрать поражение — это отдельная вещь и меряется интервью и повторным выбором, а не прогоном;
- наблюдение короткого боя не требует постоянного желания вмешаться прямой командой — измеряется долей боёв, в которых тестер запросил вмешательство. **Это же измерение решает `DEC-005`:** если доля устойчиво высока, набор рычагов расширяется до 2–3 групповых сигналов, каждый с ценой и каждый допускающий неповиновение, объяснённое трассой.

### 6.5. Deliverables

- `Combat System Spec`;
- simulation core боя;
- battle viewer;
- **модель боевых событий**: журнал с идентификаторами и провенансом — источник статуса, модификатор конкретного урона, выбранное действие. Без неё экран разбора нечем наполнить;
- **экран разбора после боя**: метр урона/лечения/поглощения плюс причинная лента. Числа здесь — свершившиеся факты, а не прогноз, поэтому `DEC-006` их не запрещает ([`DIRECTION_2026-08`](../research/DIRECTION_2026-08.md) §4.7);
- batch runner и balance report;
- набор golden scenarios;
- playtest report и решение о переходе.

### 6.6. Порядок работ

**Сначала — сквозной спайк**, как требует `AGENTS.md` §4 для риска на стыке с движком: один такт с намерением, ударом, статусом и смертью проводится из simulation core через очередь событий в Pixi; проверяются пауза, две скорости, пропуск и повтор; снимается кадр в run-smoke. Спайк нужен потому, что между «кодом» и «артом» есть третий слой — **оркестрация подачи** (синхронизация непрерывной картинки с дискретной симуляцией, порядок одновременных событий, читаемость при наложении эффектов), плюс звук и доступность (`GDD` §16.6). Замер спайка делит стоимость на simulation events, оркестрацию, VFX-ассеты, звук и полировку.

Только после этого утверждается порядок ниже — от самого выгодного к самому дорогому ([`DIRECTION_2026-08`](../research/DIRECTION_2026-08.md) §4.6):

1. механика на решётке и экран разбора после боя — это проверка читаемости, а не украшение. **Данных для него в движке нет:** существующий causal trace объясняет решение о контракте, а боевой журнал событий, провенанс модификаторов и семантику агрегатов надо спроектировать (`DIRECTION_2026-08` §4.7). До контрфактической модели формулировки остаются честными: «по замороженным целям», а не «благодаря заморозке»;
2. код-слой обратной связи: полосы, числа с контрастной обводкой, вспышки, выпады, hit-stop, частицы, тинты статусов. Снимает ощущение «статичных линий» без художника;
3. один нарисованный фон арены — главный носитель воспринимаемого качества и один статичный ассет на локацию;
4. персонажи в зафиксированном стиле — последними, уже на Vertical Slice.

Симуляция при этом дискретная (такты по решётке, целочисленная арифметика), подача — непрерывная. Граница между ними — [`ADR-002`](../decisions/ADR-002-simulation-core-boundary.md), и она уже проведена и защищена в CI.

Лаборатория остаётся схематичной по `DEC-007`: в ней проверяется, читается ли бой, а не красив ли он.

## 7. Milestone 3 — First Playable / Thin Loop

### 7.1. Вопрос

Создают ли три связанных контракта менеджерские решения и историю, которую хочется пересказать?

### 7.2. Игровой цикл

```text
контракт
  → оценка риска
  → выбор состава и условий
  → согласие героев
  → подготовка
  → экспедиция/бой
  → травмы, отношения и память
  → экономика
  → следующий контракт
```

### 7.3. Scope

- 6–8 героев;
- три последовательных контракта;
- два семейства противников;
- один заказчик и одна развивающаяся угроза;
- простые деньги, оплата, лечение и снабжение;
- травма, смерть/потеря, отказ и уход хотя бы как возможные исходы;
- отношения и ограниченная память;
- after-action report;
- короткая хроника;
- сохранение/загрузка;
- 30–45 минут на прохождение.

### 7.4. Вне scope

- полноценная карта региона;
- несколько конкурирующих фракций;
- строительство штаба;
- crafting;
- параллельные отряды;
- процедурная бесконечная кампания;
- финальное визуальное качество.

### 7.5. Exit criteria

- не менее 70% тестеров пересказывают одну причинную цепочку из двух или более контрактов;
- прошлое хотя бы один раз меняет состав или условия следующего контракта;
- игрок принимает как минимум одно решение не по максимальной боевой силе;
- незаявленная рутина не занимает более 20% времени сессии;
- проигрыш создаёт продолжение, а не обязательную перезагрузку;
- сохранение и загрузка сохраняют deterministic continuation;
- ключевой путь проходит без ручного изменения данных разработчиком.

## 8. Milestone 4 — Vertical Slice

### 8.1. Цель

Показать один законченный фрагмент игры в целевом качестве и проверить UX сложной информации.

### 8.2. Scope

- один город, штаб и одна внешняя зона;
- 8–10 героев, найм и увольнение;
- три типа контрактов;
- 3–4 семейства противников;
- одна фракция и одна региональная угроза;
- минимальная автономная цепочка мира (проверка pillar P3, [DEC-008](../decisions/DEC-008-negotiation-first-differentiation.md)): угроза или фракция действует без участия игрока → создаёт или закрывает контракт → меняет состояние локации/отношение → влияет на следующий выбор игрока;
- базовые улучшения гильдии;
- целевой визуальный язык основных экранов и боя;
- onboarding первого цикла;
- звук, обратная связь и accessibility minimum;
- telemetry для тестов;
- 60–90 минут содержимого с возможностью повторного прохождения.

### 8.3. Exit criteria

- новый игрок завершает первый контракт без внешнего объяснения;
- игрок понимает различие факта, прогноза и неизвестности;
- после боя можно проследить результат до подготовки;
- UI не требует чтения GDD или wiki;
- достигнуты целевые frame time/load time для выбранной платформы;
- нет критических потерь или повреждений сохранений;
- визуальное и звуковое направление пригодно для масштабирования.

## 9. Milestone 5 — External MVP

Целевой объём соответствует разделу 18 GDD с уточнениями по итогам предыдущих этапов:

- один регион, 4 поселения и ограниченная узловая карта;
- 3 фракции;
- ростер до 8–12 героев;
- 4 типа контрактов;
- 5–7 семейств противников;
- найм, отношения, память, травмы и уход;
- экономика и несколько улучшений гильдии;
- недельный tick в минимальной форме — генератор контрактов и развитие одной угрозы ([DEC-008](../decisions/DEC-008-negotiation-first-differentiation.md)); полная симуляция фракций — только при подтверждённом Thin Loop;
- одна развивающаяся угроза и кризис;
- короткая конечная кампания;
- after-action reports и хроника;
- базовая аналитика и crash reporting согласно платформенным решениям.

### Exit criteria

- выполнены exit criteria GDD §18.4;
- внешние тестеры проходят кампанию без ручной поддержки;
- ключевые причины churn и save-scum измерены;
- контентный pipeline выдерживает добавление сущностей без изменения core-кода;
- batch simulations и regression suite выполняются в CI или плановом pipeline;
- scope следующей версии определяется данными, а не незакрытыми основами MVP.

## 11. Порядок работы агентов

Ролей две, а не восемь. Урок Dungeon Fortress: многоступенчатый конвейер агентов (координатор, интеграционный владелец, отдельные тестовый и ревью-агенты) превращается в бюрократию, где токены уходят на процесс, а не на игру.

- **Владелец продукта** принимает блокирующие `DEC`, играет playtest и даёт go/pivot/stop по milestone.
- **Агенты** делают всё остальное — исследование, спеки, реализацию, тесты, контент — небольшими независимыми PR против компилируемых контрактов и CI.

Правила вместо конвейера:

1. Задача соответствует Definition of Ready (§12); acceptance criteria проверяются автоматически, где это возможно.
2. PR мержится по зелёному CI. Отдельное ревью обязательно только для изменений simulation core, затрагивающих детерминизм, контракты между подсистемами или формат сохранений (см. AGENTS.md).
3. Milestone закрывается playtest report и явным go/pivot/stop решением владельца — никогда только по факту реализации списка функций.

## 12. Definition of Ready для задачи

Задача готова к реализации, если:

- указаны milestone и гипотеза;
- описан пользовательский или системный результат;
- известны входы, выходы и владелец интеграции;
- все блокирующие решения приняты;
- acceptance criteria проверяемы;
- указано, что не входит в scope;
- определены необходимые fixtures/data;
- понятен способ проверки без субъективного «выглядит нормально».

## 13. Definition of Done для milestone

- критерии milestone подтверждены тестами и playtest;
- опубликован краткий отчёт с наблюдениями, а не только выводом;
- проблемные seeds сохранены как regression scenarios;
- приняты или отклонены затронутые `DEC`/`ADR`;
- scope следующего этапа пересмотрен по результатам;
- технический долг, который блокирует следующий этап, устранён или явно принят;
- владелец продукта дал go/pivot/stop решение.

## 15. Изменение плана

Любое добавление scope должно отвечать:

- какую текущую гипотезу оно проверяет;
- почему без него нельзя принять go/pivot/stop решение;
- что удаляется или переносится взамен;
- как изменяются сроки и критерии выхода.

Фраза «понадобится потом» является основанием поместить работу в backlog, а не в текущий milestone.
