# Технические правила Oath & Coin — design

> Дата: 2026-08-12
>
> Статус: draft, ожидает ревью владельца продукта
>
> Назначение: вход для `ADR-001`–`ADR-005`, `ADR-007`, `DEC-009` и правок `AGENTS.md`. Долговечная форма этих решений — записи в `docs/decisions/`, а не этот файл. Файл удаляется после того, как записи написаны (§14).

## 1. Задача

Закрыть блокирующие решения Gate 0 (`MVP_PLAN` §4.1) в части стека и определить технические правила агентской разработки так, чтобы не повторить измеренные проблемы Dungeon Fortress.

Два источника входных данных:

1. **Боли, названные владельцем продукта:**
   - **Б1 — гранулярность артефактов.** Всё упаковано в одну сцену, поэтому нельзя менять один огромный файл, а параллельная работа упирается в конфликты.
   - **Б2 — слепота агента к рантайму.** Агент не всегда понимал, что при запуске есть проблемы.
2. **Ретроспектива разработчика Dungeon Fortress** — что он взял бы и чего не брал, с замерами по репозиторию. Её главный вывод определяет структуру этого документа: **дисциплина доказательств окупилась полностью, процессная документация — нет.**

Ни Б1, ни Б2 не являются свойствами Godot. Б1 — следствие организации проекта, Б2 — следствие отсутствия правила при наличии инструмента (§7.1). Выбор стека влияет только на цену их лечения.

### 1.1. Бюджет правил

Ретроспектива замерила стоимость обратного подхода: 70 382 строки C# против 2,48 МБ документации, из которых 912 КБ — пять процессных документов, обязательных к чтению каждой координационной сессией. Сорок нумерованных процессных правил, 22 ADR, 219 Issue. Вывод автора: «их сумма стоит дороже, чем ошибки, которые они предотвращают, и вымывает время из собственной игры».

Поэтому здесь действует явный бюджет, дополняющий `AGENTS.md` §12:

- **Новое правило заводится после второго случая одной и той же боли, а не после первого.**
- **Правило, которое меняется, переписывается целиком.** Поправка, ссылающаяся на другое правило, запрещена: в DF это дало «правило 28 ослабляет ADR 0017 §5», и чтобы понять, что действует, нужен граф.
- **Один файл, а не пять.** Процесс описывают `AGENTS.md` и `MVP_PLAN` §11–§15, как и зафиксировано в `AGENTS.md` §12 п.2.

Правила §6 и §7 этого документа проходят бюджет: они лечат боли, уже измеренные в Dungeon Fortress, то есть второй случай для них — этот проект. Правила §8 взяты из ретроспективы как окупившиеся. Сверх перечисленного новых процессных правил не добавляем.

### 1.2. Скорость и расход токенов как проектное ограничение

Gate 0 — инфраструктура, а не гипотеза. Рискованный вопрос проекта сформулирован в `MVP_PLAN` §3.1 и звучит про игрока, который может объяснить решения героев; проверяется он в Milestone 1. Всё время, потраченное на гейт сверх необходимого, — это отложенная проверка того, ради чего проект существует.

Отсюда пять решений, действующих на весь проект.

1. **План несёт контракты и тесты, а не готовую реализацию.** Тест — это и есть спецификация поведения; код реализации, вписанный в план, всё равно переписывается исполнителем, но читается каждым, кто план открывает. Первая версия плана Gate 0 содержала около 2700 строк, из них большую часть — производственный код. Это двойная оплата одной работы: токенами на запись и токенами на каждое чтение.
2. **Меньше задач, крупнее и связнее.** Каждая передача между исполнителями стоит перечитывания контекста. Десять микрозадач с ревью после каждой дороже четырёх связных, у которых ревью общее.
3. **Артефакты в CI, а не в git** (§8.1). Репозиторий клонируется в worktree на каждую ветку; выход прогонов в нём накапливается и оплачивается заново при каждом клоне.
4. **Мутанты — по риску** (§8.2). Ручной мутант стоит четыре операции и не производит кода.
5. **Промежуточные документы удаляются** (§14). Спека и планы — форма передачи, а не источник истины. В Dungeon Fortress документации накопилось 2,48 МБ против 70 382 строк кода; повторять это нельзя даже хорошими документами.

Проверяемое следствие: если объём документов о том, как писать игру, начинает расти быстрее объёма самой игры, правило сработало неверно и переписывается по §1.1.

## 2. Решения к принятию

Ни одно из перечисленного пока не принято: Gate 0 закрывается ручным подтверждением владельца продукта (`MVP_PLAN` §4.3). Таблица описывает содержание будущих записей, а не их статус.

| ID | Решение |
|---|---|
| `ADR-001` | Godot 4 + C#; GDScript не используется |
| `ADR-002` | `simulation/` — .NET-библиотека с нулевыми ссылками на Godot, проверяется в CI |
| `ADR-003` | Собственный RNG (PCG32 или xoshiro256\*\*) с явными потоками; `System.Random` запрещён в core |
| `ADR-004` | Контент — JSON + JSON Schema в `content/` и `schemas/` |
| `ADR-005` | Стабильные namespaced ID, независимые от отображаемых имён |
| `ADR-007` | Конверт domain event, хранение causal trace в состоянии; идентификаторы событий и trace детерминированы |
| `DEC-009` | Шесть портретов героев в M1 как явное исключение из `DEC-007` |

По `ADR-004`: `TDD` §11.1 требует человекочитаемый формат с утверждённой схемой и диффабельность. JSON плюс JSON Schema даёт и то, и другое, имеет зрелые валидаторы под .NET и не тянет за собой движковый формат, который нельзя прочитать вне Godot.

По `ADR-005`: запись в основном ратифицирует уже сформулированные правила `TDD` §5.1, добавляя namespacing контентных ID. Отдельная запись нужна потому, что схема ID входит в блокирующий блок Gate 0 (`MVP_PLAN` §4.1) и её изменение впоследствии требует плана миграции.

По `ADR-007`: `MVP_PLAN` §4.1 включает контракт events и causal trace во второй блокирующий блок Gate 0 наравне с границей core. Запись фиксирует конверт события, структуру `DecisionResult` из `TDD` §8 и требование детерминированных идентификаторов — `Guid.NewGuid()` и системное время в core запрещены (`TDD` §7.3), поэтому идентификаторы событий и trace выдают монотонные счётчики в состоянии.

Запись также закрывает минимальную политику хранения trace, оставленную открытой в `TDD` §22: **trace хранится в состоянии целиком**, в отдельном неизменяемом хранилище, адресуемом `TraceId` из события. Альтернатива «trace живёт только в результате команды» отклонена: она оставляет в сохранённом событии висячую ссылку, и после загрузки объяснить решение уже нельзя. Агрегация trace в хронику остаётся вопросом Milestone 3.

`ADR-006` и `ADR-008` остаются зарезервированными под сохранения (Milestone 3) и тестовый тулинг (по итогам spike).

### 2.4. Чего эта таблица сознательно не содержит

Ранняя версия спеки предлагала `ADR-009` — фиксированный симуляционный тик с интерполяцией рендера, по совету ретроспективы Dungeon Fortress «разводите с первого дня».

**Решение отозвано.** `MVP_PLAN` §4.2 переносит пространство и время боя на старт Milestone 2, `TDD` §9 фиксирует эту модель как заблокированную, а Gate 0 не реализует и не проверяет тик ни одной строкой кода. Принимать решение, которого нечем подтвердить, — ровно та церемония, которую та же ретроспектива называет неокупившейся.

Риск при этом уже закрыт действующим инвариантом `TDD` §9: результат боя не зависит от frame rate и animation timing. Совет ретроспективы сохраняется как вход в решение Milestone 2, а не как решение Gate 0.

### 2.0. Отклонения от эскиза `TDD` §5–§6 и их статус

`TDD` §5 прямо предупреждает: «Имена предварительные. Нельзя считать эту схему окончательным API до принятия соответствующего ADR». Тем не менее расхождения нужно называть, а не молчать о них, иначе через месяц никто не отличит решение от недосмотра.

| Элемент эскиза `TDD` | Решение Gate 0 | Основание |
|---|---|---|
| `expected_state_version` в команде | **реализуется** | дешёвая защита от применения команды к устаревшему состоянию; без неё контракт «применяется полностью либо отклоняется» (`TDD` §6.1) не проверяется |
| `command_id` | **реализуется и сохраняется** в состоянии | иначе поле есть, а идемпотентности нет — хуже, чем его отсутствие |
| `offered_terms` в команде | **откладывается до Milestone 1** | предложенные условия — предмет модели переговоров (`DEC-008`, `BQ-004`). Вводить их форму до решения M1 значит предрешать его |
| `confidence/uncertainty` в `DecisionResult` | **откладывается до Milestone 1** | различение факта, прогноза и неизвестности — задача M4 (`MVP_PLAN` §8.3), а его модель зависит от выбора utility или rule model в M1 |
| `emitted_events` в `DecisionResult` | **реализуется, но в `CommandResult`** | события возвращает применение команды; дублировать их внутри решения значит завести два источника истины |

Отложенное фиксируется в `ADR-007` как явно исключённый scope, а не как пропуск.

### 2.1. Почему C#, а не GDScript

`TDD` §2.3 требует, чтобы симуляция работала без графического движка, а §4.1 — чтобы core не импортировал движок. GDScript этого не позволяет физически: он не существует вне Godot. C# позволяет ровно нужное — `simulation/` становится обычной .NET-библиотекой, и её тесты гоняются `dotnet test` без бинаря Godot.

Ретроспектива подтверждает это замером: в Dungeon Fortress чистая C#-библиотека без единого типа Godot дала headless-прогоны, которые агенты использовали **3515 раз**. Движок там только рисует.

Второй довод процитирован в `AGENTS.md` §10: «несовместимость подсистем должен ловить компилятор и CI, а не ревью и не память агента». Со статической типизацией это механизм; с GDScript — декларация.

Два языка не смешиваем: это удваивает контекст агента и создаёт границу, на которой он будет ошибаться.

### 2.2. Версия движка

Пинуется точная версия: **`Godot.NET.Sdk/4.7.1` и `net8.0`**. Диапазон вида «4.7.x» пином не является — смешение API внутри минорной линии остаётся возможным, а воспроизводимость сборки требует одного значения.

Совместимость не предполагается, а подтверждена: `src/DungeonFortress.Game/DungeonFortress.Game.csproj` в Dungeon Fortress уже использует `Godot.NET.Sdk/4.7.1` с `TargetFramework net8.0` и собирается на этой машине. Отдельный compatibility spike поэтому не нужен.

Пин обязателен, а не желателен: смешение API 4.6/4.7 — типовая ошибка агентов на Godot. Версия .NET SDK пинуется через `global.json` с `rollForward: disable`, чтобы patch-версия тоже не менялась молча.

### 2.3. RNG — ловушка, которую легко пропустить

`System.Random` не гарантирует одинаковую последовательность между версиями .NET, а `TDD` §7.1 требует воспроизводимости по `ruleset_version + content_version + seed`. Без собственного генератора детерминизм сломается при обновлении SDK, и причина будет неочевидной: replay перестанет сходиться без единого изменения в правилах.

Реализуем PCG32 или xoshiro256\*\* с независимыми потоками из `TDD` §7.2. Алгоритм и способ derivation потоков фиксируются в `ADR-003`.

## 3. Два тестовых контура

Ключевая структурная идея: подавляющее большинство тестов из `TDD` §15 не требует движка.

| Контур | Чем гоняется | Что покрывает | Скорость |
|---|---|---|---|
| Быстрый | `dotnet test` | unit, scenario по seed, property/invariant, batch, валидация контента — `AGENTS.md` §8 пп. 1–4 | секунды |
| Медленный | `gdUnit4` + runtime harness | адаптеры, сохранения, UI-smoke, e2e критического пути — пп. 5–6 | минуты |

Известные грабли headless-прогона Godot — обязательный warm-up-импорт, `GODOT_DISABLE_LEAK_CHECKS=1` против ложных падений от leak-логов, деградация C#-адаптера без `--headless` — касаются только медленного контура. Он остаётся маленьким, поэтому их цена ограничена.

`tools/simulation-runner` из `TDD` §14 — обычное console-приложение, а не запуск движка с флагами.

## 4. Структура репозитория

```text
OathAndCoin.sln
global.json
simulation/            # OathAndCoin.Simulation — чистые переходы состояния
content/               # JSON-контент
schemas/               # JSON Schema
adapters/              # OathAndCoin.Content — загрузка, валидация, сборка состояния
game/                  # проект Godot
  app/                 #   application layer, use cases
  ui/                  #   экраны, строятся кодом
  scenes/              #   тонкие .tscn-корни
  harness/             #   автопилот-сцены
tools/
  simulation-runner/   # console app, без Godot
tests/
  unit/  scenarios/    # быстрый контур
  integration/         # медленный контур
docs/
```

Структура следует `TDD` §20 с одним уточнением, которого там нет.

### 4.1. Почему core разделён на две сборки

`TDD` §4.1 запрещает core обращаться к файловой системе, но контент откуда-то читать надо. Если загрузчик живёт в той же сборке, что и правила, запрет становится декларацией: проверить его нечем, потому что `File.ReadAllText` в сборке уже есть.

Поэтому:

- **`OathAndCoin.Simulation`** — переходы состояния и правила. Ни файловой системы, ни часов, ни глобальной случайности, ни Godot. Проверяется механически.
- **`OathAndCoin.Content`** — чтение JSON, валидация по схемам, сборка начального `GameState`. Ссылается на `Simulation`, обратной ссылки нет.

Две сборки вместо трёх: отдельный application-слой в Gate 0 нечем наполнить, и заводить его заранее — тот же случай «понадобится потом» из `MVP_PLAN` §15.

Каталоги не создаются заранее — только вместе с первым артефактом.

## 5. Механизация границы core

`TDD` §4.1 объявляет границу прозой, а прозу агент нарушит, не заметив. Проверка читает **метаданные собранной сборки** `OathAndCoin.Simulation.dll` через `System.Reflection.Metadata` и утверждает:

1. нет `AssemblyReference` и `TypeReference` с именем сборки или пространством имён, содержащим `Godot`;
2. нет `TypeReference`/`MemberReference` на недетерминированные символы: `System.Random`; `DateTime.Now`, `UtcNow`, `Today`; `DateTimeOffset.Now`, `UtcNow`; `Guid.NewGuid`; `Environment.TickCount`, `TickCount64`; `Stopwatch`; `CultureInfo.CurrentCulture`, `CurrentUICulture`; типы файловой системы (`File`, `Directory`, `Path`, `FileStream`, `FileInfo`, `DirectoryInfo`, `StreamReader`, `StreamWriter`);
3. нет `float32` и `float64` ни в одной сигнатуре — полей, параметров, возвращаемых значений, локальных переменных.

Основание: `TDD` §7.3 и §7.4. Каждое нарушение называет найденный символ: диагностика без имени нарушителя бесполезна.

### 5.1. Почему не скан исходников

Первая версия этого раздела предписывала три текстовые проверки: граф зависимостей по `.csproj`, поиск запрещённых подстрок в исходниках и чтение `Assembly.GetReferencedAssemblies()`. Реализация была доведена до конца, после чего независимое ревью воспроизвело обходы вживую — каждый давал зелёный набор тестов при реально скомпилированном нарушении:

- ссылка на движок, объявленная в `Directory.Packages.props` или протащенная транзитивным `<Import>`, не видна сканеру `.csproj`;
- `new Random()` и `Random.Shared` не содержат подстроки `System.Random`, потому что `using System` неявный;
- `var x = 1.5;` не содержит токена `double` вообще — текстом это не ловится ни при каком списке;
- `DateTime.Today`, `DateTimeOffset.UtcNow`, `ToString("N2")` не попадали в список, а список принципиально неполон.

Вывод, стоивший одного полного цикла реализации: **эвристика по тексту применялась там, где существует семантическая проверка.** Метаданные меряют то, что действительно скомпилировалось, поэтому алиасы, неявные `using`, склейка имён через свойства MSBuild и неявная типизация перестают быть обходами.

`Assembly.GetReferencedAssemblies()` при этом строго слабее чтения метаданных и поглощается им.

### 5.2. Предел метаданных: проверять надо и поставку

Первая формулировка §5.1 утверждала, что вопрос об объявленной, но неиспользуемой ссылке снимается сам: раз её не используют, она ни на что не влияет. **Это утверждение было проверено и опровергнуто.** Ссылка, объявленная в автоимпортируемом MSBuild-файле, резолвится компилятором: `GodotSharp.dll` копируется в выходной каталог, а зависимость попадает в `deps.json`. Поставляемый артефакт оказывается связан с движком, хотя в метаданных сборки нет ни одного `TypeReference` на него.

Отсюда проверка границы состоит из двух частей, а не одной:

1. **Метаданные** — что код действительно использует (§5).
2. **Поставка** — выходной каталог и `deps.json` сборки `OathAndCoin.Simulation` не содержат имён, связанных с движком.

Область действия — **все сборки под `simulation/`**, а не одна, найденная через маркерный тип: иначе второй проект в том же каталоге выводит нарушение из-под проверки целиком.

У проверки обязан быть positive control: утверждение, что прочитана именно ожидаемая сборка и что таблицы метаданных не пусты. Без него проверка зеленеет оттого, что ничего не прочитала, — тот же дефект, что был у текстовой версии.

### 5.3. Известные пределы, которые не догоняются раундами

Статическая проверка символов принципиально не видит:

- рефлексию по имени (`Type.GetType("System.Random")`), `dynamic` и P/Invoke;
- свёрнутые и боксированные литералы плавающей точки — следа в сигнатурах не остаётся, нужен разбор IL-опкодов;
- неявную культурозависимость (`ToString("N2")`, `int.Parse(s)`) — символа не существует, культура потребляется внутри библиотеки;
- поведение сторонних сборок в рантайме.

**Guard доказывает форму кода, а не детерминизм исполнения.** Настоящий гейт детерминизма — replay-хеш канонического артефакта (§8.6). Записывается в `ADR-002` явно, чтобы guard не считали достаточным.

Неявная культурозависимость закрывается отдельным тестом: прогнать сценарий под враждебной локалью и сверить байты канонического артефакта.

Побочное следствие, зафиксированное намеренно: запрещаются **типы файловой системы**, а не всё пространство `System.IO`. Детерминированные `MemoryStream`, `StringWriter`, `BinaryWriter` разрешены — они понадобятся для канонической сериализации (§8.6), и запрещать их значило бы принять решение молча.

Одна стадия pipeline вместо абзаца в документе — принцип `AGENTS.md` §12 п.1.

## 6. Б1 — гранулярность артефактов

1. **Информационный UI строится кодом.** `.tscn` вырождается в тонкий корень, весь diff уходит в `.cs`. Для агентов это выигрыш, а не жертва: редактора они не видят и сейчас правят `.tscn` вслепую. Официальные рекомендации Godot (тонкий `Main`, самодостаточные под-сцены, данные в ресурсах) при этом остаются в силе.
2. **Лимит размера `.tscn` в CI** — по числу нод. Конкретный порог выбирается по факту первого реального экрана: выдуманное заранее число либо не сработает, либо начнёт мешать.
3. **Данные живут в `content/`**, не в `.tres` и не запечены в дереве нод. Этого и так требует `TDD` §11.
4. **Одна задача — одна сцена.** Ownership по сценам из командных практик Godot рассчитан на людей; для агентов его заменяет декомпозиция задач.

Исключение по п. 3: единственный оправданный `.tres` — `Theme` UI-kit (§12), потому что он один и меняется редко.

## 7. Б2 — runtime harness

### 7.1. Диагноз

В Dungeon Fortress harness уже построен:

| Файл | Строк | Что умеет |
|---|---|---|
| `scripts/run-game.ps1` | 336 | `--screenshot` на заданном тике, `-VisibleSmoke`, детерминированные режимы |
| `scripts/GodotTools.ps1` | 879 | захват stdout+stderr, контракт exit-кодов, матч на `ERROR:`, проверка версии |
| `scripts/HudVerification.ps1` | 391 | проверка HUD |
| `scripts/capture-evidence.ps1` | 246 | сбор артефактов прогона |

При этом `run-game` упоминается в `README.md`, `ROADMAP.md`, `GATE_DECISIONS.md` и десятках файлов `evidence/`, но в `AGENTS.md` (168 строк) и `CLAUDE.md` (16 строк) — ни разу.

Агент, читающий перед задачей ровно те файлы, которые управляют его поведением, не знал, что у него есть глаза. **Инструмент был, правила не было.**

Вывод: если портировать harness и не починить правило, боль переносится вместе с лекарством.

### 7.2. Решение

1. **Порт harness из Dungeon Fortress аудитом, а не копипастой.** Берём каркас: контракт exit-кодов, захват stderr, output guard на `ERROR:`, скриншот на тике. Не берём содержимое, заточенное под механику DF (`CameraZoom`, graybox-специфика).
2. **Одна команда без угадаек.** Вход вида `run-smoke <scenario>`, всё остальное — значения по умолчанию. Инструмент с двенадцатью обязательными параметрами агент не вызовет: он вызовет то, что помнит.
3. **Правило в `AGENTS.md` §7.** Для UI-задачи к пяти обязательным состояниям (loading, empty, error, incomplete, normal) добавляется шестое требование — **артефакт прогона**: PNG плюс лог.
4. **Проверка в CI.** PR, трогающий `game/ui/**` или `game/scenes/**`, обязан ссылаться на артефакт прогона. Без этого правило снова станет прозой.

### 7.3. Скриншот по номеру тика

Уточнение из ретроспективы, повышающее ценность harness: скриншот снимается **по номеру симуляционного тика**, а не по времени, и делается обычным скриптом.

Обоснование там же измерено: наложение текста на текст в Dungeon Fortress не поймали **десять зелёных стадий проверок** — поймал человек по кадрам. Слой представления иначе не проверяется в принципе, а привязка к тику делает кадр воспроизводимым, то есть пригодным как доказательство по §8.1.

## 8. Дисциплина доказательств

Раздел целиком взят из ретроспективы Dungeon Fortress как окупившаяся часть опыта. Автор рекомендует взять **эти четыре приёма и остановиться**; здесь они приняты без расширения.

### 8.1. Каждое число — с командой, которой оно снято

Самое дешёвое правило и ловит больше всех остальных вместе. За одну сессию оно поймало в DF: «30 открытых задач», оказавшиеся артефактом умолчания `--limit` (на деле 51); заявление «проверки зелёные» на PR, где CI этих проверок не гоняет вовсе; `sha256`, не воспроизводимый названной командой; токенные числа без источника.

Механизм работает потому, что **агент пишет уверенным тоном всегда** — правило переносит вес доказательства с тона на воспроизводимость.

Обобщение того же принципа, подтверждённое отказом domain MCP (§11.3):

> **Инструмент агента обязан оставлять воспроизводимый след, а не ответ в контексте.**

Число или наблюдение, существующее только в контексте агента, непроверяемо третьей стороной и потому доказательством не является.

**След — это CI-артефакт, а не файл в git.** Скриншоты, логи и отчёты прогонов публикуются стадией pipeline и живут в артефактах сборки: они уже привязаны к коммиту, их видит любой ревьюер, и они не раздувают репозиторий, который по §10 клонируется в worktree на каждую ветку. В git попадает только то, что является входом, а не выходом: сценарии, фикстуры, ожидаемые значения.

Правило частично записано в `AGENTS.md` §11 применительно к числам в PR; расширяется на любой инструмент и любое число.

### 8.2. Мутант там, где ошибка дорога

Формулировка существенна: **проверка не считается сделанной, пока не показано, что она краснеет.** Не «тесты проходят», а «вот подстановка, ломающая ровно это, и вот на ней красное».

Три уточнения, каждое из которых в DF куплено ошибкой:

- **мутант на каждую половину правки, а не на правку целиком** — иначе одна половина может не работать вовсе;
- **мутант запускается только после коммита проверяемого состояния** — иначе откат мутанта сносит саму правку;
- **зелёный мутант почти всегда значит, что проверка мерит не то**, а не что дефекта нет. Случай из DF: проверка «раненая рука бьёт слабее» осталась зелёной при полностью отключённой руке — разрыв 16,57 против 19,04 делал торс через готовность, а проверка приписывала его руке.

**Область действия ограничена, и это существенная часть правила.** Мутант обязателен для:

- детерминизма и воспроизводимости;
- доменных инвариантов;
- новых CI-проверок — иначе в pipeline попадает стадия, которая никогда не краснела.

Для остального достаточно обычного цикла red/green. Ручной мутант стоит четыре операции — правка, прогон, откат, прогон — и не производит ни строчки кода; требовать его на каждую половину каждой правки значит купить процесс дороже ошибок, которые он предотвращает. Это ровно тот итог, который ретроспектива Dungeon Fortress вынесла из сорока правил (§1.1), и повторять его нельзя даже приёмом, который она рекомендует.

`Stryker.NET` подключается тогда, когда объём правил сделает автоматизацию дешевле ручной дисциплины; решение — `ADR-008` по итогам спайка.

### 8.3. Индикатор, выданный за вердикт

Проверка утверждает про X, а мерит удобную близкую величину Y. Два случая из DF: расстояние до врага мерилось по прямой вместо пути (стена между ними давала ложное обвинение); «застрял из-за механики» считало всех, кто не дошёл, включая убитых по дороге.

**У агентов это системная слабость, потому что удобная величина всегда под рукой.** Искать целенаправленно.

Для нас это не абстракция: `TDD` §8 требует causal trace, соответствующий использованным данным, а `MVP_PLAN` §5.5 формулирует exit criteria M1 через поведение тестеров. И то, и другое легко подменить удобным индикатором — например, измерять «доля причин, показанных в UI» вместо «доля тестеров, назвавших две главные причины».

### 8.4. Остановка на рубеже с запиской следующему

Названо в ретроспективе «возможно, самый ценный приём из всех» для агентской разработки.

Исполнитель останавливается **до** исчерпания контекста, коммитит и пишет в файл «хождённую землю»: что проверено, что опровергнуто замером, какие варианты уже прогнаны и отвергнуты. За одну сессию в DF это дважды сэкономило полный круг — следующий агент не передоказывал сделанное и не полез в тупики, за которые уже заплачено.

Записка живёт в файле под git рядом с задачей, а не в теле Issue (§11.2, п. о теле Issue).

### 8.5. Независимый review отдельным агентом на каждый PR

Находки называет ревьюер, а не автор. Причина строгая: **сторона, чей merge разблокируется, не должна иметь права понижать находки до «неважного».** В DF этот приём поймал три блокирующих ошибки в работе самого автора ретроспективы, включая полномочия, случайно записанные шире принятого решения.

Совмещение с риск-ориентированной глубиной ревью из `AGENTS.md` §11: **инвариант — не «всегда глубоко», а «оценивает не автор».** Три тира сохраняются как есть:

- **обязательное отдельное ревью** и **лёгкое ревью** — ревьюером выступает агент, не писавший этот код;
- **«достаточно зелёного CI»** — ревьюер не назначается вовсе. Здесь вердикт выносит pipeline, а он и так не является автором.

Требовать отдельного ревьюера на механическую правку означало бы отменить третий тир, который сам появился как лекарство от конвейера (`MVP_PLAN` §11). Приём из ретроспективы лечит другую болезнь — автора, понижающего собственные находки, — и применяется там, где находки вообще бывают.

### 8.6. Что именно сравнивает replay

Тест детерминизма легко сделать зелёным и бессмысленным — достаточно сравнивать сокращённый отчёт. Тогда проверка утверждает «симуляция воспроизводима», а мерит «краткая сводка совпала»: случай §8.3 в чистом виде, на главном контракте проекта.

Поэтому разделяются два артефакта:

- **Канонический determinism artifact** — вход (команды, версии, seed) и полный выход: финальное `GameState`, все события, все traces и состояния RNG-потоков. Сравнивается он или его стабильный хеш. Это то, что проверяет `TDD` §7.1.
- **Человекочитаемый отчёт спайка** — решения, счёт, коды причин. Он для владельца продукта, а не для теста.

Смешивать их нельзя: первый должен быть исчерпывающим, второй — коротким.

### 8.7. Версия контента вычисляется, а не объявляется

Захардкоженная `content_version` — ложь, ожидающая своего часа: контент правится, версия остаётся, и заголовок replay продолжает утверждать, что данные те же.

`ContentVersion` вычисляется как digest содержимого всех контентных файлов в детерминированном порядке. Источник версии один, забыть поднять её невозможно, ручного шага не появляется. `RulesetVersion` остаётся объявленной, потому что описывает правила, а не данные, и меняется решением, а не правкой файла.

## 9. Наследство ретроспективы, отложенное до Milestone 2

Ретроспектива Dungeon Fortress называет дорогим в переделке разведение двух вещей:

1. симуляция идёт фиксированным тиком, рендер интерполирует;
2. частота тика и длительность анимации — разные числа. Грабля из DF: тик шесть раз в секунду и удар «свежий» ровно один тик — весь удар укладывался в 167 мс, из шести нарисованных поз владелец видел три и говорил «выглядит плохо».

Совет верный, но **решением Gate 0 он не становится** (§2.4). Модель времени боя закреплена за Milestone 2 в `MVP_PLAN` §4.2 и помечена заблокированной в `TDD` §9; принимать её здесь нечем подтвердить, потому что Gate 0 не пишет ни строчки боевого кода.

Раздел существует, чтобы совет не потерялся: он входит в постановку решения `G0-D2`/`G0-D3` на старте Milestone 2. До тех пор действует уже записанный инвариант `TDD` §9 — результат не зависит от frame rate и animation timing.

## 10. Изоляция работы

**Worktree на ветку; координационная рабочая копия неприкосновенна.**

Обоснование из ретроспективы: два агента в одной рабочей копии — это когда проверяющий находит дерево не на той ветке и перестаёт доверять тому, что проверяет.

Единица изоляции — **ветка или PR, а не отдельный пункт плана.** Последовательные задачи одного плана делят один worktree: они идут по очереди в одном дереве и конфликтовать между собой не могут. Worktree на каждый пункт даёт стоимость создания и удаления без единого выигрыша в изоляции.

Симптом обратного подхода наблюдаем в файловой системе Dungeon Fortress: около 130 каталогов `df-verify-*` и `_wt-*` рядом с репозиторием, плюс отдельный скрипт `check-no-worktrees-in-root.ps1`, написанный, чтобы с этим бороться. Отсюда второе требование: **worktree удаляется по завершении ветки**, и это проверяется механически.

Приём поддержан существующим тулингом владельца (`superpowers:using-git-worktrees`), поэтому новых инструментов не требует.

**Следствие для тестов.** В worktree `.git` — это файл, а не каталог. Любой поиск корня репозитория, проверяющий только `Directory.Exists(".git")`, в worktree сломается, то есть сломается везде, где по этому разделу и должна идти работа. Фикстуры тестов передаются через конфигурацию сборки, а не поиском корня по файловой системе.

## 11. Тулинг

### 11.1. Заводим

| Инструмент | Зачем | Контур | Когда |
|---|---|---|---|
| `dotnet test` + xUnit | `AGENTS.md` §8 пп. 1–2 | быстрый | Gate 0 |
| Собственный RNG | §2.3 | быстрый | Gate 0 |
| Валидация контента **тестом**, не CLI | пять стадий `TDD` §11.2 | быстрый | Gate 0 |
| `tools/simulation-runner` | режимы `TDD` §14, batch-баланс | быстрый | Gate 0 |
| Runtime harness (порт из DF) | глаза агента, §7 | медленный | перед M1 |
| `gdUnit4` | адаптеры, сохранения, UI-smoke | медленный | перед M1 |
| Property-тесты (`CsCheck`) | инварианты `TDD` §15 | быстрый | когда пространство состояний перерастёт примеры |
| `Stryker.NET` | автоматизация §8.2 | быстрый | `ADR-008` по итогам спайка |

**Валидация контента — тест, а не отдельное консольное приложение.** `TDD` §19 требует стадию валидации данных в pipeline, но не требует под неё проекта: `dotnet test` в CI уже запускается, а тест не нуждается ни в разборе аргументов, ни в контракте кодов возврата — то есть не может в них ошибиться. CLI-валидатор появится, когда появится потребитель вне CI: авторы контента или моддинг.

Общая валидация при этом живёт в одном месте. Загрузчик `OathAndCoin.Content` проверяет те же диапазоны, что и JSON Schema, а отдельный тест утверждает, что границы схемы и границы загрузчика совпадают. Иначе схема проверяет CI, загрузчик проверяет рантайм, и однажды они разойдутся молча.

### 11.2. Не заводим

Список сознательных отказов — часть решения, а не пробел в нём. Каждый пункт подкреплён измеренным результатом.

- **Отдельные арт-модели** (Midjourney, Stable Diffusion, Flux). Для шести портретов и набора иконок достаточно ChatGPT. Пайплайн под шесть картинок — случай, который `MVP_PLAN` §15 отправляет в бэклог.
- **Godot-MCP-плагины** (GDAI и родственные). Их ценность — показать агенту живое дерево сцены, но по §6 UI строится кодом и дерева там почти нет.
- **Телеметрия.** `MVP_PLAN` §10 ставит её на M1 как research.
- **Собственный domain MCP-сервер.** См. §11.3.
- **Реестр технического долга как отдельный институт.** В DF дорос до 27 записей, из которых 21 просрочена, обзавёлся правилом счёта возраста, именованными исключениями, счётчиком переформулировок и отдельным скриптом проверки колонок таблицы — то есть стал самостоятельной задачей. Пять якорей из девяти при этом вообще не имели вычислимого возраста. Правило вместо реестра: **находка без наблюдаемого последствия либо чинится сейчас, либо выбрасывается.** Список того, что никто не сделает, — это не список.
- **Журнал решений как отдельный документ, переписываемый руками.** В DF восемнадцать решений переносились агентом из Issue в файл, и review нашёл в самом переносе семь дефектов, три блокирующих. Решение живёт там, где принято; указатель на него остаётся тонким. Для нас это значит: `docs/decisions/` — место принятия, а не копия чего-то ещё.
- **Тело Issue как источник истины.** GitHub не хранит историю правок тела; в DF одной правкой были стёрты пятнадцать записей, восстановленных случайно. Всё, что важно, живёт файлом под git.

### 11.3. Domain MCP — измеренный отказ

В Dungeon Fortress существует `tools/DungeonFortress.DomainMcp`. Замер по транскриптам показал:

- вызовов от агента, решавшего задачу, — **четыре за всю историю**, все `prototype_run`;
- `simulation_run` и `bridge_status` — **ноль вызовов**;
- единственный регулярный трафик — собственная проверка живости сервера в `verify.ps1`;
- для сравнения: `dotnet test` — 5678 вхождений, headless-сценарии — 3515;
- цена содержания — 2155 строк плюс несколько стадий в каждом прогоне проверок.

Причина проигрыша структурная: сервер даёт фиксированную крупную операцию, а агенту нужна произвольная величина — то есть тест, который пишут, а не эндпойнт, который зовут. И результат MCP-вызова не оставляет следа в репозитории, то есть воюет с §8.1.

Не портируем. Доменная дисциплина, которую сервер принёс (`SchemaVersion`, стабильная точка входа, отказ на лишний аргумент), ценна и переносится в код, а не в сервер.

Граница уверенности замера: он сделан по транскриптам Claude Code и сессиям Codex на одной машине; использование из другого клиента в нём не видно.

## 12. Арт

Объём до Milestone 4: **UI-kit плюс шесть портретов героев**, ничего больше. Арт для боя — не раньше M4, согласно `DEC-007`.

**UI-kit** — типографика, цветовые токены, отступы, иконки из готового open-source набора (Lucide или Phosphor, SVG, лицензия MIT). Живёт как Godot `Theme`.

**Портреты** — разовый акт через ChatGPT, не пайплайн. Три правила, без которых он превращается в пайплайн:

- один общий шаблон промпта на всех шестерых, иначе стиль разъедется;
- фиксированный размер и кроп;
- промпты коммитятся рядом с картинками, иначе седьмого героя в том же стиле не сделать.

Ссылка на портрет — по стабильному ID героя (`TDD` §5.1), не по имени файла.

**Формальность.** `DEC-007` в статусе `accepted` говорит про M1–M3: «Никакого целевого арта». Портреты этому противоречат, поэтому требуется `DEC-009` с обоснованием через exit criteria M1 («ни один герой не описывается тестером только через класс или силу»). Без записи агент, читающий `DEC-007`, будет прав, а мы нет.

Генерация арта — build-time. Запрет `AGENTS.md` §2 на runtime LLM как источник игрового состояния она не нарушает; фиксируется явно, чтобы не обсуждать повторно.

## 13. Модели по ролям

| Модель | Зона | Роль в ревью |
|---|---|---|
| Opus (Claude Code) | контрактный пакет, `DEC`/`ADR`, спеки систем, семантика simulation core, интеграционное владение межсистемными правками | ревьюер высокорисковых PR |
| Sonnet-имплементаторы | задачи в границах готовой спеки: экраны, контент, тесты, адаптеры | ревьюер чужих PR своего тира |
| DeepSeek (OpenCode) | механика и объём: контент по существующим схемам, рутинные рефакторинги, фикстуры | исполнитель |
| ChatGPT (sol/terra/luna) | арт; внешнее второе мнение по спекам через скилл `peer` | код не мержит |

По §8.5 ревьюером PR всегда выступает агент, не писавший этот код. Роль ChatGPT как ревьюера спек существенна отдельно: модель, не участвовавшая в написании, ловит другие дыры, чем автор, — и это дёшево по сравнению с реализацией по спеке с ошибкой.

При вызове субагентов модель передаётся явно и указывается префиксом в описании (`[opus]`, `[sonnet]`) — правило из личных инструкций владельца.

**Про размер брифа.** Ретроспектива отмечает противоречие честно: бриф обязан быть самодостаточным, потому что агент не дочитает ссылки, но брифы в несколько тысяч слов дороги и нижняя половина, вероятно, не читается. Разрешаем это не длиной, а §8.4: записка о хождённой земле от предыдущего исполнителя снимает с брифа обязанность пересказывать уже проверенное.

## 14. Что происходит с этим документом

`AGENTS.md` §12 п.2 замораживает число процессных документов. Этот файл создаёт шестое дерево (`docs/superpowers/specs/`) и потому **удаляется** после того, как его содержание переедет в записи решений. Ретроспектива DF прямо называет копирование решений между документами источником дефектов (§11.2), поэтому промежуточная форма не должна пережить свою задачу.

**Правим существующие документы:**

- `AGENTS.md` §6 — информационный UI строится кодом, сцена остаётся тонким корнем.
- `AGENTS.md` §7 — DoD для UI-задачи получает шестое требование: артефакт прогона.
- `AGENTS.md` §8 — мутационная дисциплина (§8.2) заменяет нынешнее правило про snapshot-тесты, которое является её частным случаем.
- `AGENTS.md` §11 — принцип артефакта расширяется с чисел на любой инструмент (§8.1); ревьюером выступает не автор (§8.5).
- `AGENTS.md` §9 — остановка на рубеже с запиской (§8.4).
- `AGENTS.md` §12 — бюджет правил: второй случай, переписывание целиком (§1.1).
- `TDD` §21 — `ADR-001`–`ADR-005` и `ADR-007` переводятся из плана в принятые.
- `MVP_PLAN` §14 — закрыть `BQ-001`, `BQ-008`, `BQ-009`.

**Добавляем в `docs/decisions/`:** `ADR-001`–`ADR-005`, `ADR-007`, `DEC-009`. Реестр решений процессным документом не является, запрет `AGENTS.md` §12 п.2 на него не распространяется.

Шесть правок `AGENTS.md` — это много, и §1.1 требует объяснить, почему они проходят бюджет. Каждая закрывает боль, уже измеренную в Dungeon Fortress, то есть встречается второй раз. Ни одна не ссылается на другое правило: каждая переписывает свой пункт целиком.

### 14.1. Порядок принятия, а не только состав

Решение принимает владелец продукта (`MVP_PLAN` §4.3), поэтому записи не могут появиться сразу в статусе `accepted` — иначе подтверждение превращается в формальность при уже закрытом гейте.

Порядок обязателен:

1. Код и спайк готовы, CI зелёный.
2. Записи создаются со статусом **`proposed`**, со ссылками на реализацию и на тесты, которые сломаются при их отмене.
3. Владелец смотрит артефакты и даёт go/pivot/stop.
4. **Отдельным финальным коммитом** статусы переводятся в `accepted`, обновляются реестры `TDD` §21 и `MVP_PLAN` §14, удаляются временные документы.

Шаг 4 не выполняется до шага 3 ни при каком состоянии pipeline. Зелёный CI доказывает, что решение реализуемо, но не что оно правильное.

## 15. Открытые вопросы

- Конкретный порог размера `.tscn` — определяется по первому реальному экрану (§6 п. 2).
- Выбор между PCG32 и xoshiro256\*\* и способ derivation потоков — решается внутри `ADR-003`. Требование к форме уже зафиксировано: генератор counter-based, состояние потока выводится из seed, номера потока и порядкового номера решения, поэтому в состоянии не хранится изменяемый объект RNG.
- Модель времени боя, включая фиксированный тик, — Milestone 2 (§9).
- Выбор набора иконок (Lucide или Phosphor) — при сборке UI-kit, обратимо.
- Объём переносимого из harness Dungeon Fortress уточняется аудитом; оценка «дни, не недели» опирается на то, что архитектура доказана, а не измерена заново.
- Момент подключения `Stryker.NET` и property-тестов — `ADR-008` по итогам спайка.
