# Negotiation System Spec

> Дата: 2026-08-22
>
> Область: минимальный срез переговоров и обещаний ([`DEC-008`](../decisions/DEC-008-negotiation-first-differentiation.md) §1), Milestone 1
>
> Статус: спецификация до реализации. Продуктовое решение — [`DEC-012`](../decisions/DEC-012-negotiation-offer-protocol.md); снятие паритета с корпусом — [`ADR-013`](../decisions/ADR-013-retiring-corpus-parity.md)

Deliverable `MVP_PLAN` §5.6 в части модели переговоров, обещаний и их нарушения. Ядро
решения героя описывает [`HERO_DECISION_SPEC`](HERO_DECISION_SPEC.md) и не переписывается
здесь: переговоры — отдельная система **на том же ядре**, ровно как этот документ и
предполагал.

## 1. Зачем система существует

Проверяемая гипотеза (`DIRECTION_2026-08` §2.1, H-B): **понимание героя превращается в
осмысленный выбор игрока, а последствие этого выбора меняет следующий**.

Сегодня причинная петля разорвана в одном месте: трасса объясняет решение, но следующего
решения игрока нет, поэтому объяснение никому не служит. Отказ героя при этом тупик, а не
ход — ни поднять ставку, ни услышать встречное условие.

Связь с pillars: **P1** (герои — субъекты) — торг имеет смысл только потому, что оценка
условий персональна; **P2** (подготовка важнее микроконтроля) — пакет собирается до, а не
во время; **P4** (истории рождаются из систем) — нарушенное обещание порождает событие,
которое тестер пересказывает.

Чего система **не** делает: не добавляет прямого управления героями (`DEC-001`), не
показывает игроку чисел решения (`DEC-006`), не расширяет пространство переговоров
(`DEC-008` §1 разрешает расширение только после подтверждения гипотезы).

## 2. Модель данных

### 2.1. Оффер

`ContractState` получает поле `offer: OfferState`.

```ts
type OfferPhase = 'draft' | 'locked' | 'settled';

interface OfferState {
  readonly version: number;          // 1 на старте, +1 на каждую правку пакета
  readonly keyHero: HeroId | null;   // с кем идёт торг; null до первой правки
  readonly advance: number;          // аванс каждому принявшему — денежное условие
  readonly methodTag: ContentId | null; // выбранная метка — ценностное ограничение
  readonly promisedBonus: number;    // надбавка ключевому герою по расчёту; 0 = обещания нет
  readonly phase: OfferPhase;
  readonly respondedBy: SortedSet<HeroId>;
  readonly acceptedBy: SortedSet<HeroId>;
}
```

**`respondedBy` и `acceptedBy` переезжают с контракта внутрь оффера, и это несущее
решение, а не перестановка полей.** `DIRECTION_2026-08` §6.2 требует, чтобы согласие было
привязано к версии; хранение ответов на контракте выполняло бы это требование только
дисциплиной — «не забыть очистить их при правке пакета». Внутри оффера новая версия
буквально является новым объектом с пустыми множествами, поэтому устаревшее согласие не
существует: его негде хранить.

Инварианты, проверяемые при построении состояния:

- `acceptedBy ⊆ respondedBy` (как и раньше);
- `phase = 'draft'` ⇒ `respondedBy ⊆ {keyHero}` — в черновике отвечает только ключевой;
- `phase = 'settled'` ⇒ `status = 'crewed'`;
- `promisedBonus > 0` ⇒ `keyHero ≠ null`;
- `0 ≤ advance ≤ patronFee`, `0 ≤ promisedBonus ≤ patronFee`.

`ContractStatus` остаётся двузначным (`offered`, `crewed`) и отвечает на вопрос «набран ли
отряд». Фаза отвечает на другой вопрос — «где переговоры», — и третьего значения статуса
не заводится по той же причине, по какой не заводится `DeclinedBy`: два поля об одном
факте расходятся.

### 2.2. Память героя о слове гильдии

`HeroState` получает два поля:

```ts
readonly believesGuildPromises: boolean; // true у нового героя
readonly grievance: number;              // 0 у нового героя, 0..GRIEVANCE_MAX
```

Оба — состояние кампании, а не контент: они меняются по ходу игры, как `trustInGuild`, и
в файлах героев не объявляются.

Существующее `trustInGuild` для роли последствия **не переиспользуется**. Оно входит в
счёт как `trust / 10`, то есть не более десяти очков против вкладов в десятки: падение
доверия почти не изменило бы ни одного ответа, и последствие оказалось бы заявленным, а
не наблюдаемым.

### 2.3. Казна

`GameState` получает `treasury: number` — целое, может уходить в минус.

Резерв под обещанные надбавки **не хранится**: он выводится из состояния как сумма
`promisedBonus` по контрактам в фазе `locked`. Хранить его значило бы держать второй
источник правды о том же факте.

### 2.4. Контракт (схема контента 3)

```json
{
  "schema_version": 3,
  "id": "core:silence_the_cult",
  "display_name_key": "contract.core.silence_the_cult.name",
  "patron_fee": 55,
  "risk": 65,
  "required_crew": 3,
  "tags": ["target:cult", "target:temple"],
  "negotiable_tags": ["method:open", "method:deception"]
}
```

- **`payment` переименовано в `patron_fee`.** Поле изменило смысл: это больше не то, что
  видит герой, а плата заказчика гильдии за закрытое дело, то есть потолок аванса и
  надбавки. Прежнее имя стало бы уверенно написанной ложью в схеме, которую читает автор
  контента. Границы прежние — `PATRON_FEE_MIN..PATRON_FEE_MAX` (0..100), константы
  переименованы вслед за полем;
- **`negotiable_tags`** — необязательный взаимоисключающий набор ровно из
  `NEGOTIABLE_TAGS_COUNT` (2) меток, из которого игрок выбирает **одну**. Ровно двух
  хватает на срез, и число объявлено константой, а не «двумя-тремя»: третья метка
  умножает контрастные сценарии, ничего не добавляя к гипотезе. Пересечение
  с `tags` запрещено: метка, которая и так есть у контракта, не является выбором.
  Контракт без `negotiable_tags` торгуется только деньгами и обещанием — это законный
  случай, а не незаполненное поле;
- суммарное число меток (`tags` + одна выбранная) по-прежнему не превышает
  `MAX_TAGS_PER_CONTRACT`.

Реестра меток по-прежнему нет (`HERO_DECISION_SPEC` §1.1): `method:open` существует
потому, что её написали в контракте. Опечатку ловит проверка поставляемого контента, а не
загрузчик.

### 2.5. Версии форматов

| Что | Было | Стало | Почему |
|---|---|---|---|
| `SUPPORTED_CONTENT_SCHEMA_VERSION` | 2 | **3** | `patron_fee`, `negotiable_tags` |
| `RULESET_VERSION` | `m1-decision/1` | **`m1-negotiation/1`** | вход правила изменился: аванс вместо авторского числа, два новых мотива |
| `ARTIFACT_VERSION` | 3 | **4** | форма состояния другая: оффер и казна |
| `SAVE_SCHEMA_VERSION` | n | **n+1** | те же поля в снимке; окно совместимости нулевое (`ADR-006`) |

Шаг `ARTIFACT_VERSION` до сих пор был запрещён комментарием в
`determinism-artifact.ts` — «степить его значит сделать 54 байт-идентичных артефакта
формально несравнимыми и уничтожить доказательство паритета». Запрет снят
[`ADR-013`](../decisions/ADR-013-retiring-corpus-parity.md), и комментарий переписывается
вместе с числом, а не оставляется противоречить коду.

## 3. Действия игрока и переходы

### 3.1. Пять команд

| Команда | Разрешена | Что делает |
|---|---|---|
| `composeOffer` | `draft`, либо `locked` при `status = 'offered'` | задаёт `keyHero`, `advance`, `methodTag`, `promisedBonus`; `version + 1`; ответы обнуляются; фаза → `draft` |
| `proposeContractToHero` | `draft`, только `keyHero` | ключевой герой решает по текущей версии |
| `lockOffer` | `draft`, `keyHero ∈ acceptedBy` | фаза → `locked`; пакет заморожен |
| `pollCrew` | `locked`, `status = 'offered'` | весь ростер, кроме уже ответивших, решает один раз в порядке `HeroId` |
| `settleContract` | `locked`, `status = 'crewed'` | расчёт: `pay: boolean`; фаза → `settled` |

Возврат `locked → draft` через `composeOffer` — условие играбельности, а не ослабление
блокировки: без него игрок при ненабранном отряде не имеет хода вообще. Обещание при этом
не вступало в силу — сделки не было, и экран это говорит.

### 3.2. Диаграмма

```text
   composeOffer          proposeContractToHero (только keyHero)
   ┌──────────┐          ┌──────────────────┐
   │          ▼          │                  ▼
   │      ╔═══════╗◄─────┘            ╔═══════╗
   └──────║ draft ║                   ║ draft ║
          ╚═══════╝                   ╚═══╤═══╝
                                          │ lockOffer (keyHero согласился)
                                          ▼
                                     ╔════════╗
                                     ║ locked ║ status: offered
                                     ╚═══╤════╝
                                         │ pollCrew
                        ┌────────────────┴────────────────┐
        отряд не набран │                                 │ отряд набран
                        ▼                                 ▼
                   ╔════════╗                        ╔════════╗
                   ║ locked ║                        ║ locked ║ status: crewed
                   ╚═══╤════╝                        ╚═══╤════╝
                       │ composeOffer                    │ settleContract(pay)
                       └──► обратно в draft,             ▼
                            новая версия             ╔═════════╗
                                                     ║ settled ║
                                                     ╚═════════╝
```

### 3.3. Что делает каждая команда, по шагам

**`composeOffer(commandId, contractId, keyHero, advance, methodTag, promisedBonus, expectedStateVersion)`**

1. границы: `0 ≤ advance ≤ patronFee`, `0 ≤ promisedBonus ≤ patronFee`, `methodTag ∈
   negotiableTags` (либо `null`, если набора нет);
2. новая `OfferState` с `version + 1`, пустыми `respondedBy` и `acceptedBy`, фазой `draft`;
3. событие `offer_revised`, `causalTraceId = null` — решения здесь не принимал никто.

**`lockOffer(commandId, contractId, expectedStateVersion)`**

1. `keyHero ∈ acceptedBy` текущей версии — иначе `rejected.key_hero_has_not_accepted`;
2. казна покрывает обязательство: `treasury − reservedBonuses ≥ advance × requiredCrew +
   promisedBonus` — иначе `rejected.treasury_cannot_cover_the_offer`. Проверка идёт по
   `requiredCrew`, а не по числу уже согласившихся: обязательство берётся на полный отряд,
   и обнаружить нехватку после набора значило бы обещать деньги, которых нет;
3. фаза → `locked`, событие `offer_locked`.

**`pollCrew(commandId, contractId, expectedStateVersion)`**

Герои ростера, не входящие в `respondedBy`, в порядке `HeroId`. Для каждого — тот же
`decide` с тем же контекстом, что и раньше; `acceptedBy` растёт по ходу, поэтому мотив
связей видит уже согласившихся, как и прежде. Опрос **не** останавливается при наборе
отряда: остановка сделала бы ответ героя зависящим от того, сколько мест осталось, а не от
его характера, и `DEC-001` этого не разрешает. Статус переходит в `crewed`, как только
`acceptedBy.size ≥ requiredCrew`.

**Ключевой герой в этой фазе не переспрашивается, и это не исключение из «весь состав
отвечает по заблокированной версии».** `lockOffer` не поднимает версию, поэтому согласие,
на основании которого пакет заблокирован, дано ровно той версии, которая заблокирована.
Переспросить его значило бы задать один и тот же вопрос по одному и тому же пакету дважды
и получить другой ответ из-за нового настроения.

**Ординалы тратятся последовательно**, по одному решению за раз, в том же порядке
`HeroId`: расход остаётся функцией состояния, и решение, закрытое воротами, по-прежнему не
тратит ничего (`HERO_DECISION_SPEC` §5). Из этого следует свойство, которое обязано быть
проверено, а не предположено: перестановка героев в ростере меняет и ответы, и слепок —
поэтому порядок опроса фиксирован именно `HeroId`, а не порядком, в котором игрок кого-то
вспомнил.

Одна команда — несколько решений, поэтому `CommandResult.decision: DecisionResult | null`
становится `decisions: readonly DecisionResult[]`. Единственное поле пришлось бы либо
врать про число решений, либо обзавестись плюральным близнецом — вторым источником правды
об одном факте.

**`settleContract(commandId, contractId, pay, expectedStateVersion)`**

```text
treasury += patronFee − advance × acceptedBy.size − (pay ? promisedBonus : 0)
```

Если `promisedBonus > 0` и `pay = false`:

```text
victim  = keyHero
victim.believesGuildPromises = false
victim.grievance    = min(grievance + GRIEVANCE_VICTIM,  GRIEVANCE_MAX)
для каждого h ∈ acceptedBy \ {victim}:
  h.grievance       = min(grievance + GRIEVANCE_WITNESS, GRIEVANCE_MAX)
```

Событие — `contract_settled_promise_kept` либо `contract_settled_promise_broken`; при
`promisedBonus = 0` — `contract_settled`. Свидетель определяется по `acceptedBy` на момент
расчёта: он был в отряде, когда гильдия не заплатила.

Потолок `GRIEVANCE_MAX` существует, чтобы обида оставалась соизмеримой с прочими мотивами
и качественная шкала не выродилась в «крайне» на любом счётчике.

## 4. Как это входит в решение героя

Изменения в `ContractDecisionRule` — четыре, форма формулы прежняя.

| Мотив | Было | Стало |
|---|---|---|
| Выгода | `patronFee * greed / TRAIT_SCALE` | `offer.advance * greed / TRAIT_SCALE` |
| **Надбавка** | — | `offer.promisedBonus * greed / TRAIT_SCALE`, **только при `believesGuildPromises`** |
| Обида | `payment < risk` → `(risk − payment) * pride / TRAIT_SCALE` | `expected < risk` → `(risk − expected) * pride / TRAIT_SCALE`, где `expected = advance + доверяемая надбавка` |
| **Слово** | — | `−grievance`, если `grievance > 0` |
| Метка метода | — | `offer.methodTag` добавляется к `contract.tags` до проверки ворот и склонностей |

Порядок вкладов: выгода, надбавка, риск, обида, склонности, доверие, связи, слово,
настроение. Порядок попадает в трассу и потому фиксирован; деление по-прежнему применяется
к каждому слагаемому отдельно, а не к сумме.

Надбавка — **отдельный вклад, а не прибавка к авансу**, и это не косметика: сложенные, они
дали бы одну строку «выгода», из которой игрок не увидел бы, что сработало именно
обещание. Ровно эта строка — то, ради чего система построена.

Метка метода добавляется к меткам контракта **до** ворот, поэтому выбор `method:deception`
блокирует героя с принципом `core:refuses_deception` так же, как авторская метка. Кода в
правиле здесь нет: ворота и склонности уже умеют это, и трасса уже умеет это объяснять.

### 4.1. Новые коды причин

Два кода добавляются в закрытый словарь `ReasonCodes`:

- `hero.decision.promise_of_a_bonus` — положительный, источник `contract.id`;
- `hero.decision.guild_broke_its_word` — отрицательный, источник `hero.definition`.

Источники выбраны по правилу `HERO_DECISION_SPEC` §4.2: имя источника не показывается там,
где источником является сам контракт или сам отвечающий герой, — оба уже названы на
экране. Поэтому у обеих строк `sourceDisplayNameKey = null`.

### 4.2. Свойство, которое расширяется

`HERO_DECISION_SPEC` §2.5 при фиксированных seed и ординале гарантировал: рост оплаты не
превращает согласие в отказ, рост риска не превращает отказ в согласие. Утверждение
расширяется на два входа:

- рост `advance` не может превратить согласие в отказ;
- рост `promisedBonus` не может превратить согласие в отказ.

Оба держатся по той же причине, что и прежде: обе величины входят положительным вкладом и
одновременно уменьшают обиду, а ворота от них не зависят вовсе.

Отдельно **не** утверждается монотонность по метке: смена `method:open` на
`method:deception` может перевернуть ответ в любую сторону, и это ровно то, ради чего
метка сделана предметом выбора.

## 5. Что видит игрок

### 5.1. Модель экрана

`ContractOfferScreenModel` получает поля, пять состояний (`Loading`, `Empty`, `Error`,
`Incomplete`, `Normal`) остаются пятью: **фаза — поле модели, а не состояние экрана**.
Состояние отвечает на вопрос «есть ли что показывать», фаза — «на каком шаге сделка», и
смешение сделало бы `Error` частным случаем фазы.

Добавляется:

- `treasury: number` — казна числом. Объективный факт той же природы, что размер награды,
  который `GDD` §16.3 прямо оставляет числом;
- `offer: OfferLine | null` — версия, фаза, аванс числом, выбранная метка и доступные
  альтернативы ключами, обещанная надбавка числом, `keyHeroDefinition`;
- `treasuryForecast: number` — казна после расчёта, если сдержать слово. Это подача цены
  уступки из Crusader Kings III: чем платишь, видно до подтверждения;
- `promiseTerms: PromiseTermsLine | null` — **две строки, что засчитается исполнением и
  что нарушением**. Обязательны до подписания по `DIRECTION_2026-08` §6.3 и являются
  лечением отказного режима Football Manager: там обещания засчитываются нарушенными при
  выполнении, и игрок не понимает почему;
- `settlement: SettlementLine | null` — в фазе `settled` и в `locked` при набранном
  отряде: сколько обещано, кому, кто в отряде, что случится с казной при каждом из двух
  исходов.

`ResponseLine` не меняет формы: новые мотивы — обычные `ReasonLine` с обычной
качественной оценкой.

### 5.2. Тексты

Названия меток строятся по существующему правилу `tag.{namespace}.{name}` и живут в
`content/locale/` — их авторит контент. Подписи черновика, кнопок, фаз и две строки
предиката обещания живут в `ui-text/`: они появляются вместе с экраном и меняются вместе с
ним (`AGENTS.md` §6, `ADR-012`).

## 6. Edge cases и отказоустойчивые состояния

| Случай | Поведение |
|---|---|
| Правка пакета после ответа ключевого героя | новая версия, ответ обнулён; герой отвечает заново — это и есть п. 2 протокола |
| Правка пакета в фазе `locked` при набранном отряде | `rejected.offer_not_in_draft` |
| Не ключевой герой в фазе `draft` | `rejected.not_the_key_hero` |
| `lockOffer` без согласия ключевого | `rejected.key_hero_has_not_accepted` |
| Казна не покрывает обязательство | `rejected.treasury_cannot_cover_the_offer`, состояние возвращается по ссылке |
| Отряд не набрался после `pollCrew` | законное состояние: фаза `locked`, статус `offered`; игрок правит пакет новой версией. Обещание в силу не вступало |
| `settleContract` до набора отряда | `rejected.crew_not_filled` |
| Повторный расчёт | `rejected.already_settled` |
| Расчёт без обещания (`promisedBonus = 0`) | законен; `pay` игнорируется, событие `contract_settled`, обид не возникает |
| Ключевой герой заблокирован принципом на выбранной метке | обычный отказ по воротам; счёта нет, обещание не действовало |
| Герой уже не верит обещаниям | надбавка не входит в счёт **и не попадает в трассу** — вклад величиной ноль в след не пишется (`HERO_DECISION_SPEC` §2.3) |
| Контракт без `negotiable_tags` | `methodTag = null`, метки контракта не расширяются |
| Казна ушла в минус | законно, экран показывает отрицательное число. Ограничение доступа к контрактам — экономика, вне scope M1 |

Ошибки контента — на загрузке, `InvalidDataException` с текстом, называющим оба значения,
как и весь остальной контент (`HERO_DECISION_SPEC` §6). Новые проверки: `negotiable_tags`
пересекается с `tags`; в наборе меньше двух меток; выбранная метка вне набора.

## 7. Интеграция

**События** (`ADR-007`, конверт прежний): `offer_revised`, `offer_locked`,
`contract_settled`, `contract_settled_promise_kept`, `contract_settled_promise_broken`.
У всех пяти `causalTraceId = null` — их причиной является команда игрока, а не автономное
решение, и трассы у них нет по построению. Существующие `hero_accepted_contract` и
`hero_declined_contract` не меняются.

**Границы пакетов** не двигаются: `simulation` не узнаёт о контенте, `presentation` не
импортирует типы `content`, правило по-прежнему получает `DecisionContext`, а не
`GameState`. Проверка границ (`lint:deps`, `tests/architecture`) остаётся как есть.

**Сохранения:** три новых поля состояния попадают в снимок, версия схемы растёт, окно
совместимости нулевое (`ADR-006`).

## 8. Спайк до плана

`AGENTS.md` §4 требует тонкого сквозного спайка, если риск лежит на стыке с движком или
другим внешним процессом. Такой стык здесь один, и он не в переговорах: **команда,
производящая несколько решений сразу**, проходит через сессию, read model, React-приложение
и `run-smoke`, и утверждение «это просто список вместо поля» до сих пор никем не
исполнялось.

Спайк: провести выдуманную команду, возвращающую два решения, из ядра до кадра
`run-smoke` на именованном checkpoint; выбросить код. Проверяется ровно одно — что
`decisions` как список не ломает сессию, снимок дерева контролов и оба хеша.

Переговорная часть спайка не требует: она целиком внутри уже исполняемых слоёв.

## 9. Критерии готовности

- пять команд, переходы фаз и все отказы из §6 реализованы и покрыты тестами;
- согласие невозможно пережить смену версии — проверено свойством, а не примером;
- монотонность §4.2 держится по обоим новым входам;
- нарушенное обещание меняет ответ пострадавшего **и** свидетеля в сценарном прогоне;
- пять состояний экрана и три фазы сняты кадрами `run-smoke`;
- канонические слепки пересобраны **вместе с поимённым перечнем** изменившихся сценариев
  и причиной у каждого (`ADR-013`);
- `verify` зелёный без стадии паритета; дайджесты корпуса, RNG- и JCS-векторы зелёные.

## 10. Проверка

### 10.1. Свойства

- `RaisingAdvanceNeverTurnsAcceptanceIntoRefusal`;
- `RaisingPromisedBonusNeverTurnsAcceptanceIntoRefusal`;
- `PromisedBonusIsIgnoredExactlyWhenTheHeroStoppedBelieving`;
- `RevisingTheOfferLeavesNoResponseBehind` — по сгенерированным последовательностям правок;
- `PrincipleHoldsAtEveryAdvanceAndBonus`;
- `SameInputsProduceTheSameDecision` (существует, расширяется новыми входами).

### 10.2. Переходы и арифметика

`OfferProtocolTests`: каждый отказ из §6 отдельным тестом; `lockOffer` проверяет казну по
`requiredCrew`, а не по числу согласившихся; `pollCrew` опрашивает в порядке `HeroId` и не
останавливается при наборе отряда; `settleContract` считает казну по формуле §3.3;
свидетелем становится каждый из `acceptedBy`, кроме пострадавшего; обида упирается в
потолок.

### 10.3. Сценарии и контрасты

Новые сценарии с каноническими слепками: `offer_revised_resets_answers`,
`method_choice_flips_the_key_hero`, `promise_carries_a_reluctant_hero`,
`promise_kept`, `promise_broken`, `broken_word_changes_the_next_answer`,
`witness_remembers`, `crew_not_filled_reopens_the_draft`.

Контрасты (`ContrastDefinition.AllowedInputs` расширяется): `offer.advance`,
`offer.method_tag`, `offer.promised_bonus`, `hero.grievance`,
`hero.believes_guild_promises`.

### 10.4. Мутанты

Обязательны по `AGENTS.md` §8 в трёх областях, и все три здесь есть:

- **детерминизм** — `pollCrew` в обратном порядке `HeroId` обязан краснить сценарный
  слепок;
- **доменный инвариант** — сохранение `acceptedBy` при смене версии обязано краснить
  свойство `RevisingTheOfferLeavesNoResponseBehind`, а не только пример;
- **новые проверки** — удаление стадии паритета из `verify` не должно оставить `verify`
  зелёным при сломанных дайджестах корпуса.

Мутант ставится на каждую половину правки и только после коммита проверяемого состояния.

### 10.5. Плейтест

H-B измеряется на людях по двухшаговому протоколу `DIRECTION_2026-08` §7: выбор пакета и
обещания → явное последствие → второй сопоставимый выбор. Засчитывается, только если игрок
изменил второй выбор **и** может назвать связь. Ни один тест выше этого не утверждает.

## 11. Явно вне scope

MESO и подача нескольких равноценных пакетов (`DIRECTION_2026-08` §6.5); коллективный
торг; условия про состав вида «не брать X»; пересмотр уже данных согласий; встречные
требования героя; обещания об исходе экспедиции; обещания заказчикам (`D-03`); экономика
M3 и любое ограничение доступа к контрактам по казне; перенос интерфейсных ключей из
`content/locale/` в `ui-text/` — он становится возможен после `ADR-013`, но едет отдельной
задачей, а не прицепом.

## 12. Открытые вопросы

- `ASSUMPTION`: `GRIEVANCE_VICTIM`, `GRIEVANCE_WITNESS`, `GRIEVANCE_MAX` и стартовая
  казна — авторская настройка первого приближения. Проверяются плейтестом; заменяются
  замером доли добровольных нарушений при явной выгоде (`DIRECTION_2026-08` §7), а не
  спором;
- `D-02` закрыт наполовину: черновик — обычный путь предложения, а не отдельный режим.
  Нужна ли кнопка «предложить как есть» — по итогам плейтеста;
- `D-04` (видит ли игрок цену обещания заранее) в срезе не решается: `treasuryForecast`
  показывает цену в монетах, но не цену в отношении героя;
- называть ли свидетелю, чьё именно обещание нарушено, — сегодня нет; строка говорит, что
  гильдия нарушила слово, но не чьё. Расширение меняет форму `ReasonLine` и оба хеша.
